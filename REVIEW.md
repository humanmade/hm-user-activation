# Review

## What failure looks like here
- An activation page that shows two outcome groups at once (success and error, or "resent" next to a result), or none when one is expected.
- A form or message that tells an anonymous visitor whether an email address or username has a pending signup or account.
- A signup that can't be activated or recovered (expired link with no working resend, key rotated under the user).
- Placeholders or bound URLs that point somewhere different from what the settings page says.

## Always check
- `filter_block_visibility()` and every group variation: which request (GET `?key`, POST key, POST resend, redirect flag) shows which group, on the activation page and off it.
- Signups are network-wide (`$wpdb->signups`); options and pages are per site. Check which blog's settings an email or link uses.
- User signups (`domain = ''`) and blog signups both reach this plugin's emails and activation page.
- Nonces on every POST handler, `wp_unslash` + sanitise on every superglobal, `$wpdb->prepare` on every query.
- New block: `src/blocks/<dir>/` with `block.json`, `render.php` and an ESM `index.js` whose `save` returns null, plus `register_block_type()` on `build/blocks/<dir>` in the main file. A new editor-only script needs its own entry in `webpack.config.js`.
- Build output: `build/` is git-ignored, so check that whatever ships the plugin (release ZIP via `git archive`, Composer installs, tags) gets a built `build/`, and that `.gitattributes` keeps `src/` and build config out of the archive.
- Email templates: every placeholder in a default body is filled in every code path, and the settings help text lists it.
- New options: `register_setting()` with type, sanitiser and default, plus a matching `get_option()` default.
- Back-compat: compare against the `1.0.0` tag for option names, placeholders, block names, binding sources and the old public classes; a renamed option or changed stored data needs an upgrade step in `includes/upgrade.php` (with a `DB_VERSION` bump), not a runtime read fallback.
- Workflows with a write token (`contents: write` or similar): `npm ci --ignore-scripts`, and `persist-credentials: false` on checkout where the job allows it, so dependency install scripts never see the token.

## Paths that need a person
- `includes/activation.php` (account activation and auto-login)
- `includes/password-reset.php` (password reset keys)
- `includes/resend.php` (unauthenticated email sending, key rotation)

## Skip
- `build/` (generated by `npm run build`, git-ignored) and `package-lock.json`.

## Nits
- Cap 3. phpcs (HM standard) has many pre-existing errors; report only violations a change adds, and only if they differ from the existing file conventions.

## Learned
- 2026-10-21: A real signup's username hold follows `registered`, and `Resend\resend()` rewrites `registered` when it rotates an expired key (anyone can trigger it from the resend form). Any plugin-side mirror of core's 2-day hold, such as the same-response reservation transient, must survive that refresh or it drifts apart from the real row.
- 2026-10-21: Routes that ignore same-response mode (mode-off sites, `wp-signup.php` on 'all' networks) already show core's email errors directly, so a reservation they don't enforce is not an extra leak there. Don't flag it.
- 2026-10-21: Same-response mode keeps usernames unique (maintainer decision): username taken and reserved errors show, and the hidden path for a known address reserves its username for two days with a site transient, so the next attempt answers the same. A reuse rule was tried and dropped: the losing signup could not recover, and it let a block signup take a username held by a pending blog signup, which core then activates for whoever owns the username. Don't suggest reuse again.
- 2026-10-21: Same-response mode (registration form) must give the same *later* responses too, not just the current one: a path that skips `wpmu_signup_user()` leaves the username unreserved, so a second submit with that username shows whether the first address was known. Also check other routes to core's errors (`wp-signup.php` POSTs with `stage`, which the redirect lets through).
- 2026-10-21: Same-response mode strips core's email errors by count, relying on the "already registered" then "pending" checks being the last `user_email` errors in `wpmu_validate_user_signup()` (identical in 6.9.7 and 7.1). Recheck when the supported core range changes.
- 2026-10-21: The `build-to-release-branch` action needs an existing `release` branch that is an ancestor of `main` but not equal to it (`release == main` makes `git apply` fail on an empty diff). Don't flag the one-time `git push origin main:release` before a merge as a bug.
- 2026-10-21: `.github/scripts/stamp-version.sh` sets every built `block.json` version at release (core uses it as the block stylesheet `?ver=`), so the hand-set versions in `src/blocks/*/block.json` only matter on `main` and `dev-release`.
- 2026-10-21: Release tags (PR #11) are cut by `release.yml` as a commit off `main` that force-adds `build/` and stamps `__VERSION__`; that commit is reachable only from the tag, by design. `main` and the `release` branch keep `Version: __VERSION__` (the constant is unused at runtime), so don't flag that.
- 2026-10-21: The pinned build-to-release-branch action (hm-github-actions 04c32a9) fails at `git apply` ("No valid patches in input") when `release` and `main` point at the same commit; it works once `main` has moved past `release`. It needs the workflow's own checkout first, because its "Configure git" step runs before its checkout.
- 2026-10-21: An expired activation key gets its own message ("has expired"), not the generic invalid one, by design: only the key holder sees it. Don't report it as enumeration.
- 2026-10-21: For a blog signup (`domain != ''`) whose `user_login` already exists, core's `wpmu_activate_signup()` returns success with the existing user's ID (only user signups get `user_already_exists`). Network admin site-new.php and WP-CLI create users without clearing stale signups. Any code that sets a password, logs in or writes meta for the returned `user_id` must check the account is the signup's own.
- 2026-10-21: PR #9 (src/build move) was accepted without a release workflow because the next PR adds a build-before-tag Release workflow and `.gitattributes` export-ignore rules before any tag is cut. Once that has merged, report any change that lets a release ship without `build/`.
- 2026-10-21: Blocks and variations moved from hand-written ES5 (`blocks/`, `js/`) to `src/` built by `@wordpress/scripts` 27 into `build/`. Compare a changed editor script against its built output, not just the source.
- 2026-10-21: 1.0.0 data is migrated once by `includes/upgrade.php` (admin_init for manage_options, plugin activation, WP-CLI), tracked by `hm_activation_db_version`. A missing runtime read fallback for a migrated 1.0.0 option, and the front-end window before an admin visit, are by design; don't flag them. Only the non-page `hm_activation_login_url` keeps a runtime fallback.
- 2026-10-19: A class `HM\UserActivation\Activation` and the namespace `HM\UserActivation\Activation\` coexist safely (`use` + `Activation\fn()` hits the function, `Activation::m()` the class); don't flag that as a collision.
- 2026-10-19: Legacy option fallbacks are invisible in the settings UI; check help text such as "Defaults to ..." still holds when a 1.0.0 option is set.
- 2026-10-19: Rate limits on unauthenticated forms: check that an attacker cannot use up the legitimate user's allowance (per-signup caps), and that an IP limit keyed on REMOTE_ADDR is not one shared bucket behind a proxy.
- 2026-10-19: Expiry is only enforced on the plugin activation page; the wp-activate.php bypass is documented in the README, so do not report it as a new bug. Per-site lifetime vs network-wide signups is a known gap.
- 2026-10-19: Resend is unauthenticated (logged-out nonces are shared). Judge it per victim address over time: key rotation can invalidate a pending link, and refreshing `registered` keeps the signup alive forever.
